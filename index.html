Selected work

Interlock

2026–ongoing

A runtime firewall that stops AI agents from exfiltrating secrets. A Go MCP proxy tracks sensitive values through 13 registered encodings and refuses to forward exfiltrating tool calls; eBPF traces connect() and write() underneath to catch the side channels the proxy cannot see. Containment defers roughly 100ms after a trip: a deliberate tradeoff, proof over speed, so a payload receipt exists before SIGKILL fires.

Enforces

  • Encoding-aware value tracking across 13 registered forms — base64, hex, URL-encoding, reversal, and gzip, brotli, zstd and lz4 — including depth-5 nests and secrets split across calls via a session fragment buffer
  • Syscall-level egress detection via cilium-ebpf, correlating connect(), sendto() and write() by PID, with a tunable payload capture window (payload_capture_bytes, default 512)
  • Sensor-only Kubernetes DaemonSet with PID-to-pod attribution, validated on EKS (AL2023/containerd); a Unix-socket taint bridge from the proxy lets the least-privilege capabilities posture reach EXFIL verdicts without privileged /proc reads
  • Prometheus metrics, OCSF SIEM export, Slack and PagerDuty trip webhooks
  • Evaluated against 15 attack reconstructions spanning 7 disclosed CVE families: 12 reached an EXFIL verdict, with zero false positives across 37 benign scenarios and three detection gaps documented rather than closed
  • 336 Go tests behind CI race and benchmark gates, including known-gap tests that assert what each detector misses; ~0.5ms overhead engine-on versus passthrough on sensitive reads (a local benchmark, not a production SLO)

Known gaps

  • Semantic or paraphrased exfiltration is out of scope for the EXFIL verdict: a secret described in natural language, carrying no registered byte form, will not be proven. Value overlap stops at depth-5 nests, and the compressed forms are precomputed byte-exact, so they match an attacker who compresses the secret alone with the same library at the same level and miss otherwise
  • eBPF contains by killing after a correlated connect() and write(), not before the first packet; in-kernel blocking via LSM/KRSI is not shipped. IPv6, sendmsg and writev are untraced, and DoH/DoT is explicitly out of scope

Go · eBPF · Kubernetes · Prometheus

Zenith

2025–2026

A Zanzibar-inspired authorization database answering "does subject S have relation R on object O" over a relation-tuple graph. It began on CockroachDB; the version that taught me anything is the one where I replaced that with a Raft implementation written from the paper, because borrowing someone else's consensus meant never having to understand the part I actually wanted to understand.

Enforces

  • Recursive relation-tuple expansion (Zanzibar-style) with cycle detection over a DAG of usersets
  • Raft across 3 to 5 nodes: pre-vote, joint-consensus membership changes, learners, ReadIndex reads, log compaction and InstallSnapshot
  • MVCC storage, so a check reads a consistent snapshot without blocking concurrent writes
  • Reverse expansion (list all subjects with a relation) alongside forward checks
  • KV operation histories checked for linearizability with Porcupine across 2,000 deterministic simulation seeds

Go · gRPC · Raft · MVCC

Arbor

2026

A SQL query engine over Apache Arrow and Parquet, written from scratch: parser, logical planner, rule-based optimizer, and a pull-based Volcano executor. No DataFusion or Polars in the execution path: the point was owning the whole planner-to-executor route.

Enforces

  • Predicate pushdown, projection pruning, constant folding
  • Inner joins over equi predicates, GROUP BY aggregates, ORDER BY/LIMIT
  • Module boundaries checked in CI: the parser cannot reach storage, the planner cannot reach Parquet I/O, the executor cannot reach the AST
  • No unwrap in library code; clippy and rustdoc both run with warnings denied
  • The optimizer is worth 3.2x on a synthetic TPC-H-style Q6 at ~900k rows, measured with Criterion as optimizer-on versus optimizer-off on the same engine (not a comparison to any other system)

Known gaps

  • SELECT only. No subqueries, HAVING, DISTINCT, set operations, or outer joins at execution
  • Rule-based optimizer: there is no cost model

Rust · Apache Arrow · Apache Parquet

Dispatch

2026

A multi-tenant webhook delivery platform. The interesting bug was a probe-stampede race in the half-open circuit breaker: concurrent recovery probes could all fire on a dead endpoint at once. Fixed with a conditional UPDATE, single-flighted via ClaimProbe, that lets exactly one signed event probe a recovering endpoint.

Enforces

  • Single Kafka retry topic with retry_after; exhausted events land in a Postgres DLQ, chosen over a Kafka topic so replay gets filtering and pagination
  • tenant_id kept off ingest metric labels to protect Prometheus cardinality
  • REST and gRPC ingest share one internal service path; HMAC-signed delivery with idempotency keys, retries and dead-letter replay
  • Crash recovery validated by SIGKILLing the consumer under load, then reconciling all 16,001 published events against delivery-attempt and dead-letter records: zero events left without an attempt
  • ~50 events/sec sustained ingest (750 requests, 100% 202), delivery p99 ~2.5ms with 99.7% of deliveries under 2.5ms (measured on local Docker Compose under vegeta; the AWS deployment is not load-tested)
  • Provisioned on AWS with Terraform (EKS with IRSA, MSK, RDS, S3), deployed with Helm, instrumented with Prometheus

Go · Kafka · PostgreSQL · Redis · Terraform · AWS

Ratchet

2026

An incremental ELT sync engine and connector SDK in Java 21. The whole design turns on one rule: the sync cursor advances only after the data is durable, so a crash replays a window of work instead of skipping it. The failure mode I wanted was duplicated effort, never silent loss.

Enforces

  • Cursor advance gated on durability, so every crash window replays rather than dropping rows
  • Verified at 500,000 rows through 50 seeded SIGKILLs, checksums matching on every run
  • Apache Arrow in memory, Parquet on disk
  • A connector SDK, so adding a source is an implementation against an interface rather than a change to the engine

Java 21 · Apache Arrow · Apache Parquet · JUnit
